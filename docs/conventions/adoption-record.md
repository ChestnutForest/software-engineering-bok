# 採用の記録

**手法が「どこでどう使われているか」を、手法エントリ側に記録するための枠組み。**

手法エントリは「その手法が何か」を述べる。採用の記録は「あるプロダクトが
その手法をどこまで使っているか」を述べる。**この2つは別のことである。**

## なぜ `status` と分けるのか

| 欄 | 表すもの | 例 |
| --- | --- | --- |
| `status` | **本リポジトリ**がその手法をどう扱うか | `referenced-only`（権利未確認のため参照のみ） |
| `adoption` | **あるプロダクト**がその手法をどこまで使っているか | `tailored`（本来の用途から広げて使っている） |

混ぜると判断を誤る。たとえば UML は本リポジトリでは `status: registered` だが、
`paper-repro` では言及1件のみで採用していない。**`status` が `registered` であることは、
どこかで使われていることを意味しない。**

## 出所は常に別にある

**手法エントリは採否を決める文書ではない。** 採否の根拠はプロダクト側の文書が持つ。

採否を変えるときは、**プロダクト側の根拠のある文書を先に直し、そこから反映する。**
手法エントリを先に直すと、根拠のない記録が残る。

`adoption` には必ず `source` と `verified` を持たせ、どの文書のいつ時点の
記録に依るかを示す。

---

## Front Matter

```yaml
adoption:
  - product: paper-repro
    state: tailored
    scope: 本来の用途（変更箇所の特定）から、工程の進捗管理へ用途を広げている
    artifacts:
      - docs/traceability-matrix.md
    source: docs/methodology-map.md
    verified: 2026-09-11
```

配列である。**複数のプロダクトを並べられる。**

### `state`

| 値 | 意味 |
| --- | --- |
| `adopted` | そのまま採用している |
| `indirect` | 他のプロダクトや文書を経由した間接採用。直接適用ではない |
| `partial` | 一部だけ採用している。または別の仕組みが同じ役割を担う |
| `tailored` | **本来の用途や前提から変えて使っている。** 読み替えの内容を必ず書く |
| `referenced` | 言及はあるが使っていない |
| `not-adopted` | 検討したうえで採らなかった |
| `out-of-scope` | プロダクトの前提と合わないため対象にならない |
| `untraced` | **検討の記録が無い。** 却下したのではなく、痕跡が無い |

`not-adopted` と `untraced` を区別する。**前者は判断した記録があり、後者は無い。**

### `scope`

**何を採ったかを書く。** 「採用している」だけでは範囲が分からない。
工程成果物の名称、要素の区分、体系の名前など、具体を書く。

### `artifacts`

プロダクト側のリポジトリからの相対パス。**その手法が実際に現れている文書**を挙げる。

### `source` と `verified`

どの文書の、いつ時点の記録に依るか。**走査した日付を書く。**
`verified` が古くなったら、採否が変わっている可能性がある。

## 本文の節

Front Matter の下、`## 書かないもの` の前に置く。

```markdown
## 採用の記録

枠組みは [`docs/conventions/adoption-record.md`](...) が定める。

| プロダクト | 状態 | 範囲 |
| --- | --- | --- |
| [paper-repro](...) | **テーラリングあり** | ... |

### 該当する成果物

- [`traceability-matrix.md`](...)

### 前提の読み替え

母体が無いため、変更箇所の特定という本来の用途では使えない

### 読み替えにより失われるもの

**変更の影響範囲を示す機能。新規開発では影響を受ける既存箇所が存在しない**

### 出所

[`methodology-map.md`](...) 第1節。2026年9月11日の走査による。
**本エントリは採否を決める文書ではない。**
```

### 「読み替えにより失われるもの」を必ず書く

`state: tailored` のとき、**何を得たかだけでなく何を失ったかを書く。**

手法を本来と違う用途に使うと、本来の目的が果たせなくなる。それを書かないと、
**読んだ人はその手法が本来の役割を果たしていると誤解する。**

例として、`paper-repro` は合意成熟度の3レベルをトレーサビリティ・マトリクスの
工程へ読み替えている。得たのは工程を表す尺度であり、失ったのは
**合意形成の度合いという本来の意味**である。個人開発では合意する相手がいない。

## 走査のしかた

採用状況は文書の記述を読むだけでは分からない。

- **「準拠」と書いてあっても実際に使っていない**ことがある
- **書いていなくても使っている**ことがある

出現箇所を走査し、**出現数ではなく文脈で判別する。**

```
Get-ChildItem -Path <product>\docs -Recurse -File -Filter *.md |
  Where-Object { $_.FullName -notmatch '\\(devlog|history)\\' } |
  Select-String -Pattern '<手法名>' |
  Select-Object Path, LineNumber, Line
```

`devlog/` と `history/` は経緯の記録であり、現在の採否を表さないため除く。

---

## 更新の順序

1. プロダクト側の根拠のある文書が変わる
2. プロダクト側の対応表（`methodology-map.md` など）に反映する
3. **その後で**手法エントリの `adoption` を直す

**この順序を逆にしない。** 手法エントリは横断の一覧であり、一次の記録ではない。
