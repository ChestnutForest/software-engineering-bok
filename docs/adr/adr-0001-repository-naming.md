# ADR-0001 リポジトリ名の選定

## 1. 背景

姉妹プロジェクト `paper-repro` の
[`docs/references-usdm-ipa.md`](https://github.com/ChestnutForest/paper-repro/blob/main/docs/references-usdm-ipa.md)
に、要求仕様と設計に関する一次情報をまとめてある。扱っているのは次の4つである。

| 対象 | 内容 |
| --- | --- |
| USDM | 清水吉男氏の要求仕様記述法。要求・理由・説明・仕様グループ・仕様の5要素階層 |
| XDDP | 派生開発プロセス。USDM はその3点セットの1つにあたる |
| 機能要件の合意形成ガイド（IPA、2010年3月） | 対象工程は**外部設計工程**。6技術領域の分冊と概要編からなる |
| 発注者ビューガイドライン（2007〜2008年） | 上記ガイドの前身。技術領域は3つ |

これ以外の工程、すなわち実装・テスト・リリース・運用などのメソドロジーを
別のリポジトリへ集約したい。そのリポジトリの名前を決める必要がある。

## 2. 決定

**`software-engineering-bok` を採用した。** GitHub 上に作成済みである。

BoK（Body of Knowledge＝知識体系）という語により、特定のツールやトレンドに
依存しない体系的な整理であることを示す。SWEBOK Guide（IEEE Computer Society、
最新は v4.0 / 2024年）と同じ系譜の語彙を用いることで、読み手が扱う範囲を
推測しやすくなることを意図した。

ただしこの名前には既知の弱点がある。第5章に記す。

## 3. 検討した候補

10案を挙げ、それぞれの選定理由・概要・懸念を整理した。

### 3.1 一覧

| # | 候補 | 評価 |
| --- | --- | --- |
| 1 | `sdlc-knowledge-base` | 次点。全工程前提 |
| 2 | `software-engineering-bok` | **採用** |
| 3 | `software-process-playbook` | `processloop` と語が被る |
| 4 | `end-to-end-se-practices` | E2E テストと誤読される |
| 5 | `dev-methodology-archive` | GitHub の Archived と衝突 |
| 6 | `rigorous-dev-methods` | 形式手法と誤読される |
| 7 | `system-delivery-framework` | framework が成果物に見える |
| 8 | `quality-driven-development` | 新手法の提唱に見える |
| 9 | `se-lifecycle-handbook` | 全工程前提 |
| 10 | `continuous-engineering-guide` | IBM 製品名と紛れる |

### 3.2 各案の詳細

#### 1. `sdlc-knowledge-base`

- **選定理由** ソフトウェア開発ライフサイクル（SDLC）全体を網羅することを
  最も直接的に表せる。
- **概要** 要件定義・設計から実装、テスト、リリース、運用保守までの全フェーズを
  フェーズ順に集約する標準的なナレッジベース。
- **懸念** 全工程を含む前提の名前である。下流工程限定と確定した場合は合わない。
  `sdlc` を初見で読めない読み手がいる。

#### 2. `software-engineering-bok`（採用）

- **選定理由** BoK という語により、SWEBOK と同様の厳密かつ体系的な整理で
  あることを示す。
- **概要** 特定のツールやトレンドに依存しない、ソフトウェア工学の普遍的な
  メソドロジーとプラクティスを整理する。
- **懸念** `bok` 単独の略記は一般的ではない。また SWEBOK Guide v4.0 は要件から
  運用・保守まで18の知識領域を含むため、下流工程限定とした場合は名前が
  実体より広く見える。

#### 3. `software-process-playbook`

- **選定理由** 「プロセス」で各工程に焦点を当て、「プレイブック」で実践的な
  手順書であることを表す。
- **概要** どのフェーズでどの手法を選択・実行すべきかをまとめた実践ガイド。
- **懸念** 「software process」は SEI の PSP/TSP 文脈の語であり、別リポジトリの
  `processloop`（PSP/TSP 支援ツール）と混同しやすい。

#### 4. `end-to-end-se-practices`

- **選定理由** 上流から下流まで一気通貫でカバーすることを強調する。
- **概要** 理論を実装、テスト自動化、継続的デリバリー、運用まで繋げるプラクティス集。
- **懸念** ソフトウェア分野で E2E は「E2E テスト」を強く連想させる。`se` が
  software engineering と systems engineering のどちらとも読める。名前が長い。

#### 5. `dev-methodology-archive`

- **選定理由** 古典から現代まで幅広い手法を記録・保管・参照する場所という
  ニュアンスを持たせる。
- **概要** 構造化手法から CI/CD まで、様々な開発メソドロジーの文献と解説の集積庫。
- **懸念** GitHub には Archived repository（凍結状態）という機能上の意味がある。
  更新し続けるものに archive を冠すると誤解を招く。

#### 6. `rigorous-dev-methods`

- **選定理由** 厳格な仕様記述を好むアプローチと一貫性を持たせる。
- **概要** 形式的・体系的なアプローチに基づく手法のまとめ。
- **懸念** rigorous は英語圏で formal methods（Z、VDM、TLA+ 等）を強く連想させる。
  USDM は要求を階層化する**記述法**であって形式手法ではないため、看板と中身が乖離する。

#### 7. `system-delivery-framework`

- **選定理由** 実装以降は「システムを届けて稼働させる」ことが主目的となるため、
  その枠組みであることを示す。
- **概要** 組み上げ、品質担保、リリース、運用までのプロセスを構造化する。
- **懸念** framework は「枠組みそのものを提供する成果物」に見え、文献を集める
  実態とずれる。delivery が継続的デリバリーと紛れる。

#### 8. `quality-driven-development`

- **選定理由** 全工程が最終的に目指す「品質」を軸に据えることを宣言する。
- **概要** 全工程を通して品質をいかに作り込むかという視点でまとめる。
- **懸念** TDD / BDD / DDD と同型で、新しい開発手法の提唱に見える。知識を集める
  リポジトリの名前としてはミスリードになる。後からスコープを広げにくい。

#### 9. `se-lifecycle-handbook`

- **選定理由** 行き詰まった際や次フェーズへ移る際にすぐ参照できる手引書であることを示す。
- **概要** 各段階で何を参照し、どの技法を使うべきかの実用リファレンス集。
- **懸念** 全工程前提。`se` の曖昧さは案4と同じ。

#### 10. `continuous-engineering-guide`

- **選定理由** 実装以降は一度で完了せず継続的にループするという性質を表す。
- **概要** 運用監視のフィードバックを次の要件・設計へ活かす循環を解説する。
- **懸念** IBM の Engineering Lifecycle Management 系の製品名と紛れる。また
  「次の要件・設計へ活かす」時点で上流を含む前提になっている。

## 4. 検証で判明した論点

候補の検討中に、名前の選択より先に効く論点が4つ見つかった。

### 4.1 既存文書は「解説」ではなく「参照集」である

`references-usdm-ipa.md` の実体は、①一次資料の URL 一覧、②採用範囲の記録、
③使用条件（著作権）の3つである。「参照の原則」として、一次資料に当たること、
本文の転記と翻案を避けることが定められている。

とくに機能要件の合意形成ガイドは**改変・翻案が明示的に禁じられている**ため、
`paper-repro` ではコツの本文を転記も言い換えもしていない。参照するのは
著作物にあたらない事実（技術領域の区分、成熟度のレベル名、作業の区分、
工程成果物の名称）に限っている。

本リポジトリも同じ制約の下にある。`bok` / `knowledge-base` / `handbook` という
名前は「自分で解説を書き集める」方向へ運用を引きずるため、注意が要る。
名前は運用方針を規定してしまう。

### 4.2 工程で境界を引くと破綻する

XDDP は3点セットを持ち、変更要求仕様書から変更設計書、コーディング留保、
統合・テスト、正式文書の更新までをまたぐ。工程で線を引くと、こうした
複数工程にまたがる手法の置き場が決まらない。

境界は「工程」ではなく「一次情報の出所」または「プロダクト」で切るほうが破綻しない。

### 4.3 スコープが未確定である

本リポジトリが上流工程（要件定義・設計）を含むのか含まないのかは、まだ確定していない。

- **含まない場合** 案1・4・9・10 は前提が合わない。採用した `software-engineering-bok`
  も名前が実体より広くなる。
- **含む場合** `paper-repro` の `references-usdm-ipa.md` との重複が生じる。移設するのか
  相互参照にとどめるのかを決める必要がある。

### 4.4 二次情報に見つかった誤りを繰り返さない

`references-usdm-ipa.md` は、調査の過程で二次情報に次の誤りを見つけ、一次資料で
訂正したことを記録している。

- 機能要件の合意形成ガイドの技術領域を**7つ**とする記述（正しくは6技術領域＋概要編）
- 対象工程を**要件定義**とする記述（正しくは**外部設計工程**）

本リポジトリの文書でも同じ誤りを書かないこと。

## 5. 決定の結果

### 5.1 採用した名前の既知の弱点

| 弱点 | 緩和策 |
| --- | --- |
| `bok` 単独の略記が一般的でない | README の1行目で BoK を展開して書く |
| SWEBOK と同じ語彙のため全工程を含むように見える | README でスコープを1文で宣言する |
| 「解説を書く」方向へ運用を引きずる | README で転記・翻案をしない方針を明記する |
| 既存リポジトリ（`paper-repro`、`processloop`）より名前が長い | 許容する。変更しない |

### 5.2 引き受ける運用

1. README 冒頭にスコープと「本文を転記・翻案しない」方針を1文ずつ書く。
2. `paper-repro` の `references-usdm-ipa.md` と相互リンクする。既存文書は移設元・
   移設先を明記する運用を採っているため、これを引き継ぐ。
3. 著作権表示が要る資料は、出典表記をそのまま記す。
   例: 機能要件の合意形成ガイド ver.1.0、Copyright©2010 IPA

### 5.3 採用しなかった代替案

実体（一次情報の参照集）に寄せるなら、次の名前のほうが整合する。将来リポジトリ名を
見直す場合の候補として記録しておく。

| 候補 | 理由 |
| --- | --- |
| `se-references` | 既存の `docs/references.md` と同じ語彙。短い |
| `sdlc-references` | 全工程を対象とする場合。`se` の曖昧さを回避できる |
| `dev-method-sources` | 転記ではなく参照であることを名前で示せる |
| `downstream-references` | 下流工程限定と確定した場合。境界が名前で読める |
| `method-primary-sources` | 「一次資料に当たる」原則をそのまま名前にしたもの |
