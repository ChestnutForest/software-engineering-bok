# REV-0005 XDDP 追加版の構成案に対する検証

## 1. 検証の対象

XDDP を追加したリポジトリ構成として生成された案を検証した。案の骨子は次のとおり。

- XDDP を `03-team-processes/xddp/` に配置する
- その下に `traceability-matrix/` と `process-guidelines/` の2つを置く
- 選択ガイドに「新規開発か派生開発か」という判断軸を加える
- Layer 03 × Layer 04（USDM）、Layer 03 × Layer 05（PSP）の連携を描く

## 2. 判定の要約

| # | 指摘 | 重大度 |
| --- | --- | --- |
| 1 | REV-0004 で直した16点がすべて元に戻っている | 重大 |
| 2 | XDDP の3点セットのうち2つが欠けている | 重大 |
| 3 | コーディング留保が表現されていない | 重大 |
| 4 | 「新規か派生か」を層の中に埋めている。これは新しい軸である | 重大 |
| 5 | USDM と XDDP の関係を「連携」と誤って弱めている | 中 |
| 6 | 一次資料（AFFORDD）への言及がない | 中 |
| 7 | PSP との組み合わせに裏づけがなく、権利上の制約にも触れていない | 中 |
| 8 | XDDP だけディレクトリが深く、粒度が揃っていない | 小 |

XDDP を `03-team-processes` に置くという**判断そのものは妥当である。** 問題は、
その下に何を置くかと、XDDP が持つ性質をどの軸で表すかにある。

## 3. 重大な指摘

### 3.1 REV-0004 で直した16点がすべて元に戻っている

構成案は REV-0004 以前のツリーを土台にしている。そのため次がすべて再発している。

- `docs/` が無い（ADR と REV の置き場が失われる）
- 葉がディレクトリのまま（解説を書く運用を招く）
- `iso9000/`、`object-oriented/`、`software-product-line/` の表記
- UML の置き場が無い
- `spec-driven/` が `05-personal-discipline` にある
- `structured-methods（JSD等）` が1つにまとまっている
- 要件工学が設計・実装層の下にある
- 連番が 01〜05 のまま

個別の理由は REV-0004 第5章に記した。**本書では XDDP 固有の指摘に集中し、
土台は REV-0004 の構成を前提とする。**

### 3.2 XDDP の3点セットのうち2つが欠けている

XDDP の中核は「3点セット」である。

| 確認すること | 成果物 |
| --- | --- |
| What / Why — 何を、なぜ変えるか | **USDM 形式の変更要求仕様書** |
| Where — どこが影響を受けるか | **スペックアウト ＋ トレーサビリティ・マトリクス（TM）** |
| How — どのように変えるか | **変更設計書** |

構成案が置いたのは `traceability-matrix/` と `process-guidelines/` の2つだけである。

- **変更設計書が無い。** コード変更の方法を実装前に記述するもので、XDDP の
  「How」を担う。省略できない。
- **スペックアウトが無い。** TM を作る前段の作業である。TM だけを置くと、
  対応づける対象をどう洗い出すかが抜ける。

`process-guidelines/` という一般名のディレクトリは、この不足を隠してしまう。
**XDDP の骨格は3点セットなので、ディレクトリもその形にする。**

### 3.3 コーディング留保が表現されていない

3点セットを**レビューしてからコードを変更する**という規律を「コーディング留保」と
呼ぶ。「見つけ次第コーディング」による誤りと手戻りを防ぐことが狙いであり、
XDDP を XDDP たらしめている中核の概念である。

構成案の解説は「ソースコードを直接触る前に変更箇所の特定と影響範囲の分析に
リソースを集中させる」と書いており、内容としては近い。しかし**名前を挙げていない**
ため、構成にも項目として現れていない。

姉妹プロジェクトでは、コーディング留保を承認ゲートで部分的に代替したことを
記録している。**名前で引けなければ、この対応づけができない。**

### 3.4 「新規か派生か」を層の中に埋めている

構成案はこの判断軸を導入した点で評価できる。実務上もっとも効く区別である。
しかし**扱い方が誤っている。**

「新規開発か派生開発か」は、チーム層に属する性質ではない。次のように、
複数の層をまたいで効く。

| 層 | 新規開発 | 派生開発 |
| --- | --- | --- |
| チーム | RUP、スクラム | **XDDP** |
| ソフトウェア | 要件定義から設計 | **変更要求仕様書、スペックアウト** |
| 再利用戦略 | 都度開発 | **SPLE** |

REV-0002 で SPLE と XDDP の対象が重なることを既に指摘した。両者が重なるのは、
**どちらも「派生」という同じ軸の値を持つから**である。

したがってこれは **第8軸「開発の起点」**として立てるべきものであり、
Layer 03 の内部事情として扱ってはならない。

## 4. 内容上の誤り

### 4.1 USDM と XDDP の関係を「連携」と弱めている

構成案は「USDM は XDDP の中で仕様変更を記述する際の中核手法として連携」と書き、
Layer 04 と Layer 03 の連携として描いている。

**関係はもっと強い。USDM 形式の変更要求仕様書は、XDDP の3点セットの1つである。**
並列のものが協力しているのではなく、**一方が他方を構成要素として含んでいる。**

USDM を Layer 04、XDDP を Layer 03 に置いたうえで「連携」と呼ぶと、この包含関係が
見えなくなる。**ツリーが表現できない関係であり、Front Matter で補う必要がある。**
第6章に `relates_to` を追加する。

### 4.2 一次資料への言及がない

本リポジトリと姉妹プロジェクトは「一次資料に当たる」を原則としている。
XDDP の一次資料は次のとおりで、構成案はどれにも触れていない。

| 資料 | 位置づけ |
| --- | --- |
| AFFORDD（派生開発推進協議会）の公開資料 | 公式の配布元。概論＆入門ワークショップ資料が最初に読むもの |
| 清水吉男『「派生開発」を成功させるプロセス改善の技術と極意』技術評論社, 2007 | **XDDP の原典** |
| 清水吉男『【改訂第2版】要求を仕様化する技術・表現する技術』技術評論社, 2010 | **USDM の原典** |

加えて、AFFORDD には適用事例の資料がある。自治体向け Web システムへの適用事例は
**XDDP が組込み専用ではない**ことを示しており、選択ガイドの記述の裏づけになる。

**ディレクトリを用意するだけでは一次資料にたどり着けない。** 各ファイルの
`sources` にこれらを書く。

### 4.3 PSP との組み合わせに裏づけがなく、権利上の制約にも触れていない

構成案は「XDDP の枠組みの中で、見積もりや欠陥混入の防止に PSP を適用する」という
連携を提案している。着想としては自然だが、2つ問題がある。

1. **裏づけがない。** XDDP と PSP を組み合わせた実践の一次資料を確認していない。
   確認できるまでは**構想であることを明記する**か、書かない。
2. **権利の制約に触れていない。** PSP のスクリプトとフォームは CMU の特別許諾下に
   あり、派生や改変には SEI の書面許可が要る。「XDDP の中での PSP の使い方」を
   書き下ろすことは翻案にあたりうる。REV-0002 の決定6により `referenced-only` とする。

REV-0002、REV-0003 に続き、**PSP の権利制約が3回連続で抜けている。**

### 4.4 その他

- **`rup/` に「主に新規開発向け」と注記した点は妥当。** ただし RUP は現在活発に
  更新されていない。`status` に加えて、レガシーである旨を README に書く。
- **XDDP だけ2階層深い。** 他の手法が1階層なのに XDDP だけ孫ディレクトリを持つ。
  ただし3点セットを持つ XDDP は例外的にディレクトリが妥当なので、**深さではなく
  中身を揃える**方向で解決する。第5章参照。
- **「アーキテクチャとして最も美しく」** は評価の根拠がない。REV-0002、REV-0003 でも
  同種の表現を指摘した。判断を曇らせるため書かない。

## 5. 修正した構成（XDDP 部分）

REV-0004 の構成を前提に、`30-team/` を次のとおりとする。

```text
├── 30-team/                              # チーム開発プロセス層 (Mid)
│   ├── README.md                         # この階層の定義と境界
│   ├── rup.md                            # 参照のみ。IBM proprietary。レガシー
│   ├── tsp.md                            # 参照のみ。CMU のサービスマーク
│   └── xddp/                             # 3点セットを持つため例外的にディレクトリ
│       ├── README.md                     # 全体像、母体の前提、組込み専用でないこと
│       ├── change-request-spec.md        # 変更要求仕様書（USDM 形式）— 3点セット①
│       ├── spec-out-and-tm.md            # スペックアウトと TM — 3点セット②
│       ├── change-design-doc.md          # 変更設計書 — 3点セット③
│       ├── coding-restraint.md           # コーディング留保
│       ├── process-separation.md         # 変更プロセスと機能追加プロセスの分離
│       └── pfd.md                        # PFD（Process Flow Diagram）
```

**ディレクトリを作る条件を定める。** 葉はファイルを既定とし、
**3点セットのように内部構造が公式に定義されているものだけ**ディレクトリにする。
ディレクトリにする場合は `README.md` で内部構造の出典を示す。

## 6. Front Matter の拡張

### 6.1 第8軸「開発の起点」

```yaml
axes:
  paradigm: null
  design_approach: null
  process: xddp
  notation: null
  reuse: null
  practice: null
  origin: derivative        # 第8軸。greenfield / derivative / both
```

| 値 | 意味 | 例 |
| --- | --- | --- |
| `greenfield` | 新規開発を前提とする | RUP |
| `derivative` | 既存の母体を前提とする | XDDP、SPLE |
| `both` | どちらでも使える | USDM、TDD、PSP |

**XDDP は母体が無いと適用できない。** 姉妹プロジェクト `paper-repro` は新規開発で
あるため、XDDP のうち採用できたのは USDM と TM の2つだけである。この事実は
`origin` の値があって初めて説明できる。

### 6.2 `relates_to`

ツリーで表せない関係を記す。

```yaml
relates_to:
  - id: MTH-0001            # USDM
    relation: contains
    note: 3点セットの1つ（変更要求仕様書）にあたる
  - id: MTH-00NN            # SPLE
    relation: alternative-to
    note: どちらも派生を扱うが、SPLE は資産の計画、XDDP は変更の実行
```

`relation` に使う値を次のとおり定める。

| 値 | 意味 |
| --- | --- |
| `contains` | 構成要素として含む |
| `contained-by` | 構成要素として含まれる |
| `requires` | 前提として必要とする |
| `alternative-to` | 同じ問題に対する別の解 |
| `succeeds` | 後継である |

## 7. 選択ガイドへの反映

構成案が提案した「新規開発か派生開発か」は、`guides/selection/` に次の形で入れる。

1. `origin` を最初に決める。ここで `derivative` なら、選べる `process` が
   XDDP に絞られ、`reuse` に SPLE が候補として立つ
2. `origin` が決まってから、残りの軸を選ぶ
3. `combinations.md` に「XDDP は母体が無いと選べない」という制約を書く

**`origin` は他の軸より先に決まる。** 単一のマトリクス表にせず、
順序のある手順として書く理由がここにある。

## 8. 本リポジトリへ反映する決定

| # | 決定 |
| --- | --- |
| 1 | **XDDP は `30-team/xddp/` に置く。** 配置の判断は構成案のとおり妥当 |
| 2 | **3点セットを構成に反映する。** 変更要求仕様書、スペックアウトと TM、変更設計書の3つを揃える |
| 3 | **コーディング留保、プロセスの分離、PFD を項目として立てる** |
| 4 | **第8軸「開発の起点」を追加する。** 値は `greenfield` / `derivative` / `both` |
| 5 | **Front Matter に `relates_to` を追加する。** ツリーで表せない包含関係を記す |
| 6 | **ディレクトリにしてよいのは、内部構造が公式に定義されているものだけ** |
| 7 | **PSP との組み合わせは書かない。** 一次資料で裏づけが取れるまでは構想にとどめる |
| 8 | **各ファイルの `sources` に AFFORDD の公開資料と原典書籍を記す** |

## 9. 着手の順序への影響

REV-0004 第8章の順序は変えない。ただし4件目以降を次のとおり具体化する。

1. ADR-0002 でスコープを決める
2. `docs/conventions/` を書く（第8軸と `relates_to` を含める）
3. `references-usdm-ipa.md` の移設可否を決める
4. `40-software/requirements/usdm.md` を1件だけ作り、形式を検証する
5. `30-team/xddp/README.md` と `change-request-spec.md` を作る。
   **USDM との `relates_to: contains` が正しく書けるかを、ここで検証する**
6. 残りの3点セットとコーディング留保を埋める

**手順5が形式の試金石になる。** USDM と XDDP の包含関係は、ツリーだけでは
表せない代表例だからである。ここが書ければ、他の関係も書ける。
