# REV-0001 メソドロジー選択ガイドとリポジトリ名の再検討に対する検証

## 1. 検証の対象

次の問いに対して生成された回答を検証した。

> メソドロジーとしてドメイン駆動開発、オブジェクト指向開発、構造化手法開発、
> テスト駆動開発、Spec駆動開発、AI駆動開発、UML、SysML、RUP、ソフトウェア
> プロダクトラインなどがある。開発するプロダクトがどのメソドロジーを選択するのが
> 適切かを解説したガイドも含める場合、先に挙げた候補のどのリポジトリ名が最適か。

回答の骨子は次のとおりである。

1. 最適は `software-process-playbook`
2. 次点は `software-engineering-bok`
3. 実用性重視なら `se-lifecycle-handbook`
4. おまけとして `software-methodology-compass`、`dev-methodology-landscape` を提案

## 2. 判定の要約

| # | 指摘 | 重大度 |
| --- | --- | --- |
| 1 | 決定済みの名前を、決定を参照せずに覆そうとしている | 重大 |
| 2 | 第1位の推薦が、前回の検証で退けた理由を無視している | 重大 |
| 3 | 未確定のスコープを確定済みとして議論している | 重大 |
| 4 | 列挙された10項目を同じ層のものとして扱っている | 重大 |
| 5 | BoK の性格を取り違えている | 中 |
| 6 | 個別の例示に裏づけがない | 中 |
| 7 | 著作権と転記の制約に触れていない | 中 |
| 8 | XDDP と SPLE の重複を見落としている | 中 |
| 9 | 陳腐化しやすい項目への備えがない | 小 |

## 3. 重大な指摘

### 3.1 決定済みの名前を、決定を参照せずに覆そうとしている

リポジトリ名は [ADR-0001](../adr/adr-0001-repository-naming.md) で
`software-engineering-bok` に決定済みであり、GitHub 上に作成も済んでいる。

回答はこれを参照せず、別の名前を第1位として推薦している。名前を変えるなら、
変更の利益と次のコストを比べたうえで判断する必要があるが、回答にはその比較がない。

| 変更のコスト | 内容 |
| --- | --- |
| クローン済みリポジトリのリモート URL 変更 | 手元の作業ディレクトリを設定し直す |
| ADR-0001 の書き直し | 決定記録そのものが無効になる |
| 外部リンクの維持 | GitHub はリダイレクトするが、恒久的な保証ではない |

**判定**: 回答は「まだ名前が決まっていない」という誤った前提に立っている。

### 3.2 第1位の推薦が、前回の検証で退けた理由を無視している

`software-process-playbook` は前回の検証で次の理由により退けた。

- 「software process」は SEI の PSP/TSP 文脈の語である。
- 別リポジトリ `processloop`（PSP/TSP 支援ツール）と語が被り、区別がつきにくい。

回答はこの点に一切触れず、プレイブックの語源（アメリカンフットボールの戦術書）を
根拠に第1位としている。語源の説明そのものは正しいが、**退けた理由に反論していない**
ため、推薦の根拠として成立していない。

### 3.3 未確定のスコープを確定済みとして議論している

ADR-0001 第6章の未決事項1「上流工程を含むかどうか」は未確定である。

ところが今回列挙された10項目は、次のとおり大半が上流工程に属する。

| 上流寄り | 下流寄り | どちらにも属する |
| --- | --- | --- |
| DDD、オブジェクト指向、構造化手法、UML、SysML、RUP | TDD | Spec 駆動、AI 駆動、SPLE |

上流を含めないと決めた場合、この一覧の大半は本リポジトリの対象外になる。
**名前を議論する前に、スコープを確定させなければならない。** 回答はこの順序を
逆にしている。

### 3.4 列挙された10項目を同じ層のものとして扱っている

回答は10項目をすべて「メソドロジー」と呼んでいる。しかし実際には層が異なる。

| 対象 | 層 | 種別 |
| --- | --- | --- |
| 構造化手法 | 分析・設計 | 技法群（DeMarco、Yourdon ほか） |
| オブジェクト指向 | パラダイム | 考え方 |
| ドメイン駆動設計（DDD） | 設計アプローチ | 考え方とパターン言語 |
| UML | 記法 | モデリング言語（OMG）。プロセスを規定しない |
| SysML | 記法 | UML プロファイル（OMG）。システムズエンジニアリング向け |
| RUP | プロセス | プロセスフレームワーク（IBM）。事実上レガシー |
| テスト駆動開発（TDD） | 実装プラクティス | XP 由来の進め方 |
| ソフトウェアプロダクトライン（SPLE） | 再利用戦略 | 組織と資産の戦略（SEI） |
| Spec 駆動開発 | 実装プラクティス | 2025年以降の AI コーディング文脈の語 |
| AI 駆動開発 | 総称 | 市場用語。定義が定まっていない |

回答も「パラダイム（OOP、構造化）、プロセス（RUP、TDD）、モデリング（UML、SysML）」
と層の違いに半ば気づいているが、**TDD をプロセスに分類している点が誤り**であり、
より重要なことに、**そこから結論を引き出していない**。

層が違うということは、**これらは互いに排他ではない**ということである。DDD と UML と
TDD は1つのプロダクトで同時に使える。「どれを選ぶか」という単一選択の問いは
成立しない。正しい問いは「どの軸で何を選び、どう組み合わせるか」である。

回答はこの誤りを「メソドロジー選択のマトリックス表」という提案まで持ち込んでいる。
単一の表では表現できない。

## 4. 内容上の誤り

### 4.1 BoK の性格の取り違え

回答は BoK を「関係性や適用範囲、長所・短所を含めて体系化したもの」と説明し、
選択ガイドとの親和性が高いと述べている。

実際には、SWEBOK Guide は18の知識領域について**主要概念を要約し、詳細は参考文献の
一覧で示す**という構成である。IEEE Computer Society はその目的を、分野の内容を
定義すること、世界共通の理解を促すこと、他分野との境界を明確にすること、教材と
カリキュラムの土台を提供すること、認定を支えること、としている。

つまり BoK は**分類と指し示しのための記述的な文書**であって、状況に応じてどれを
選ぶかを助ける規範的な文書ではない。回答の「親和性が高い」という論拠は成り立たない。

加えて、今回の10項目は SWEBOK v4 の知識領域でいえば主に
Software Engineering Models and Methods、および Software Engineering Process の
2領域に収まる。18領域のうち2領域を扱うものに `-bok` を冠することになる。
これは ADR-0001 第5.1章に記録した弱点「SWEBOK と同じ語彙のため全工程を含むように
見える」を裏づける事実であり、緩和策（README でスコープを1文で宣言する）を
確実に実施する理由になる。

### 4.2 個別の例示に裏づけがない

回答は選択の例を3つ挙げている。

| 例示 | 判定 |
| --- | --- |
| 複雑な業務ドメインなら DDD | 妥当。Evans の主張と整合する |
| 組み込みで派生製品が多いなら SPLE | 妥当。SEI の枠組みと整合する |
| 要件が厳格なハードウェア協調システムなら SysML と RUP | **裏づけがない** |

3つ目が問題である。SysML がシステムズエンジニアリング向けである点は正しいが、
RUP と組み合わせる根拠が示されていない。RUP は IBM が策定した反復型プロセスで
あり、現在は活発に更新されていない。ハードウェア協調や安全性が要る領域で実際に
参照されるのは、機能安全の規格群やV字モデル、MBSE の実践であって、RUP ではない。

**記法（SysML）とプロセス（RUP）を並べて「選択する」と書いていること自体が、
第3.4章で述べた層の混同の表れである。**

### 4.3 用語

- 元の問いにあった「SyML」は **SysML**（Systems Modeling Language、OMG）の誤記である。
  回答は黙って訂正しているが、本リポジトリの文書では正しい綴りと策定主体を明記すること。
- 「TDD/Spec駆動」をひとまとめにしている箇所がある。Spec 駆動開発は GitHub が
  2025年9月に公開した Spec Kit や AWS の Kiro に代表される、AI エージェントへ
  仕様を渡す進め方を指す語であり、TDD とは由来も対象も異なる。並置は避ける。

## 5. 抜けている観点

### 5.1 著作権と転記の制約

ADR-0001 第4.1章に記録したとおり、姉妹リポジトリは**本文の転記と翻案を避ける**
運用を採っている。今回の10項目は、この制約がより強く効く対象を含む。

| 対象 | 権利者と注意点 |
| --- | --- |
| RUP | IBM の proprietary な成果物。教材の再配布はできない |
| SPLE | SEI / カーネギーメロン大学。資料ごとに固有の許諾条件がある |
| UML、SysML | OMG。仕様書は入手できるが本文は著作物である |
| DDD | Evans の書籍。要約の粒度によっては翻案にあたる |

**「メソドロジーを解説するガイド」を書くという発想そのものが、この制約と衝突する。**
回答はこの点に一切触れていない。本リポジトリでは、各手法の解説を書くのではなく、
一次資料へのリンクと、独自に構成した判断軸を置く形にとどめる必要がある。

### 5.2 XDDP と SPLE の重複

SPLE は派生製品の再利用戦略であり、`paper-repro` 側で扱っている XDDP（派生開発
プロセス）と対象が重なる。どちらも「既存資産から派生を作る」問題を扱う。

ADR-0001 第4.2章で述べた「工程で境界を引くと破綻する」という論点が、ここで
具体化した。SPLE をどちらのリポジトリへ置くかは、未決事項2として引き続き残る。

### 5.3 陳腐化しやすい項目への備え

Spec 駆動開発と AI 駆動開発は、2025年以降に広まった語であり、ツールも語義も
短期間で変わる。`references-usdm-ipa.md` が URL の確認日を記録しているのと同じく、
これらの項目には**確認日を必ず添える**。添えられないものは登録しない。

## 6. 検証の結論

回答のうち採用できるのは、`software-engineering-bok` を推す論拠の一部（多岐の
レイヤーにわたるものを整理する器としてふさわしい）だけである。第1位の推薦、
例示の3つ目、選択マトリクスの構想は、いずれもそのままでは採用できない。

## 7. 本リポジトリへ反映する決定

| # | 決定 |
| --- | --- |
| 1 | **リポジトリ名は変更しない。** ADR-0001 の決定を維持する。名前の弱点は同第5.1章の緩和策で扱う |
| 2 | 選択ガイドは**単一選択の表ではなく、軸ごとの選択と組み合わせのガイド**として構成する |
| 3 | 各手法は**層を明示して登録する。** 層を書かない登録は認めない |
| 4 | 各手法の**解説は書かない。** 一次資料へのリンクと、独自に構成した判断軸を置く |
| 5 | 陳腐化しやすい項目には**確認日を添える** |

決定2で用いる軸は次のとおりとする。

| 軸 | 選択肢の例 | 排他性 |
| --- | --- | --- |
| パラダイム | 構造化 / オブジェクト指向 / 関数型 | ほぼ排他 |
| 設計アプローチ | DDD / トランザクションスクリプト | 部分的に排他 |
| プロセス | RUP / スクラム / XDDP / V字 | ほぼ排他 |
| 記法 | UML / SysML / Mermaid / 独自 | 併用できる |
| 再利用戦略 | SPLE / 都度開発 | 排他 |
| 実装プラクティス | TDD / Spec 駆動 / AI 駆動 | 併用できる |

軸のあいだには依存がある。たとえば DDD はオブジェクト指向を前提とし、SysML は
システムズエンジニアリングの文脈を前提とする。**軸を独立に選べるわけではない**点を
ガイドの冒頭で明記する。

## 8. ADR-0001 の未決事項への影響

| # | 未決事項 | 本検証による変化 |
| --- | --- | --- |
| 1 | 上流工程を含むかどうか | **優先度が上がった。** 今回の一覧は上流寄りであり、これが決まらないと登録可否を判断できない |
| 2 | 複数工程にまたがる手法の置き場 | **具体例が増えた。** XDDP に加え SPLE が該当する |
| 3 | `references-usdm-ipa.md` の移設可否 | 変化なし |
| 4 | 文書の粒度と命名規則 | **本文書で `rev-*` を先行使用した。** 決定時に追認すること |
