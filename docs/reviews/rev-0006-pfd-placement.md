# REV-0006 PFD 追加版の構成案に対する検証

## 1. 検証の対象

PFD を追加したリポジトリ構成として生成された案を検証した。案の骨子は次のとおり。

- PFD を XDDP の配下に置かず、`03-team-processes/process-design-and-modeling/pfd/` として独立させる
- PFD を「開発プロセス自体をモデリングする手法」と位置づけ、Z 言語や Alloy による
  形式的モデリングになぞらえる
- PFD × メソドロジー、PFD × XDDP、PFD × PSP の3つの連携を描く

## 2. 判定の要約

| # | 指摘 | 重大度 |
| --- | --- | --- |
| 1 | REV-0005 の指摘が1件も反映されていない | 重大 |
| 2 | PFD を記法ではなくプロセスとして扱っている | 重大 |
| 3 | 形式手法との対比が PFD の性質を過大に述べている | 重大 |
| 4 | 中身が1つしかないディレクトリを作っている | 中 |
| 5 | 連携の例に、既に2度指摘した誤りが再発している | 中 |
| 6 | テーラリングの説明が、記録されている事例と違う | 中 |
| 7 | PSP の権利制約が4回連続で抜けている | 中 |
| 8 | PFD の動作の説明に出典がない | 小 |

PFD を独立して扱いたいという**着想そのものは検討に値する。** ただし独立させる
理由づけと、独立させるべき時期が誤っている。

## 3. 重大な指摘

### 3.1 REV-0005 の指摘が1件も反映されていない

構成案の `03-team-processes/xddp/` は、REV-0005 で検証した案とまったく同じである。

| REV-0005 の指摘 | 反映 |
| --- | --- |
| 3点セットのうち変更設計書とスペックアウトが欠けている | **未反映** |
| コーディング留保が項目として立っていない | **未反映** |
| 変更プロセスと機能追加プロセスの分離が無い | **未反映** |
| 「新規か派生か」を第8軸として立てる | **未反映** |
| USDM と XDDP の包含関係を `relates_to` で表す | **未反映** |

加えて REV-0004 の16点も再び元に戻っている（`docs/` が無い、葉がディレクトリ、
`iso9000/`、UML の置き場が無い、`spec-driven/` の位置、連番 01〜05、
要件工学が設計・実装層の下にある）。

**2回連続で同じ構成案が出ている。** 検証結果を土台にしないまま積み上げると、
同じ指摘を繰り返すことになる。本書では PFD 固有の論点に集中する。

### 3.2 PFD を記法ではなくプロセスとして扱っている

構成案は PFD を `03-team-processes/` の下に、RUP、TSP、XDDP と並べて置いている。
しかし**この4つは種別が違う。**

| 対象 | 種別 |
| --- | --- |
| RUP、TSP、XDDP | プロセス。開発の進め方そのもの |
| **PFD** | **記法。プロセスを記述するための図法** |

PFD はプロセスを**記述する**ものであって、プロセス**である**わけではない。
UML がソフトウェアを記述する記法であってソフトウェアの作り方ではないのと同じ関係である。

REV-0001 第3.4章で「層が違うものを同一平面に並べている」ことを指摘し、
REV-0004 で `kind` を必須項目にしたのは、まさにこの取り違えを防ぐためである。

**`kind: notation` として登録する。** 第6章に `notation_of` の追加を提案する。

### 3.3 形式手法との対比が PFD の性質を過大に述べている

構成案は次のように書いている。

> ソフトウェアの振る舞いを Z 言語や Alloy などで形式的にモデリングするように、
> 開発プロセス自体をモデリングし、曖昧さを排除する手法が PFD である

**この対比は成立しない。**

| | Z 言語、Alloy | PFD |
| --- | --- | --- |
| 意味論 | 数学的に定義されている | 定義されていない |
| 検証 | ツールによる機械的な検査ができる | できない |
| 記法 | 形式言語 | 成果物と作業を矩形と矢印で結ぶ図 |

PFD は成果物と作業の依存関係を明示する図法であり、**曖昧さを減らす効果はあるが、
排除するものではない。** 形式手法と並べると、読み手は検証可能性を期待してしまう。

REV-0001 第4.1章で、USDM を形式手法と取り違える誤りを指摘した。
**同じ種類の取り違えが、対象を変えて再発している。** REV-0004 で
`formal-methods/README.md` に USDM との違いを明記すると決めたが、
**PFD との違いも併せて書く必要がある。**

## 4. 配置についての判断

### 4.1 中身が1つしかないディレクトリを作っている

構成案は `process-design-and-modeling/` を作り、その下に `pfd/` だけを置いている。
中身が1つのディレクトリは、階層を1段増やすだけで何も分類していない。

REV-0004 の決定3（葉はファイルとし、ディレクトリはさらに分ける必要が生じたときだけ）と、
REV-0005 の決定6（ディレクトリにしてよいのは内部構造が公式に定義されているものだけ）の
両方に反する。

### 4.2 では PFD をどこに置くか

独立させたいという着想は理解できる。PFD は XDDP の中で使われるが、XDDP 専用ではない。
しかし**今は独立させる時期ではない。**

| 判断 | 理由 |
| --- | --- |
| **当面は `30-team/xddp/pfd.md` に置く** | 一次資料が XDDP の文脈にあるため。AFFORDD の概論資料と原典書籍がそれにあたる |
| `kind: notation` とする | 種別は記法である |
| `relates_to` で XDDP 外でも使えることを記す | ツリーの位置と、適用範囲の広さを分けて表す |
| **2件目のプロセス記法が登録された時点で昇格する** | そのとき `30-team/process-notations/` を作り、PFD を移す |

**昇格の条件を先に決めておく。** 条件を決めずに「独立させたほうが体系的だから」と
ディレクトリを作ると、中身が1つの階層がリポジトリ全体に増えていく。

## 5. 連携の例に含まれる誤り

### 5.1 「IPA 要件定義書」は存在しない

構成案は PFD の例として次の連鎖を挙げている。

> 入力: [IPA 要件定義書] → プロセス: [USDM による仕様化] → 出力: [USDM 仕様書]
> → プロセス: [JSD（構造化手法）による設計]

**「IPA 要件定義書」という成果物は無い。** IPA の機能要件の合意形成ガイドの
対象工程は**外部設計工程**である。

これは姉妹プロジェクトの `references-usdm-ipa.md` が「調査の過程で二次情報に
見つかった誤り」として名指しで訂正している当の誤りである。同ファイルは
「対象工程を要件定義とする記述」を、技術領域を7つとする誤りと並べて挙げている。

REV-0001 第4.3章で既に指摘した。**今回は成果物名として書かれており、
より踏み込んだ誤りになっている。**

### 5.2 JSD を構造化手法の代表として扱っている

REV-0003 第4章、REV-0004 第5章で指摘済み。JSD（Jackson System Development）は
DeMarco や Yourdon 系の構造化分析・設計とは別系統の手法である。**3回目の指摘となる。**

加えて、USDM で仕様化したものを JSD で設計するという連鎖に裏づけがない。
**PFD の説明のために、確認していない手法の連鎖を例に使わない。**

### 5.3 テーラリングの説明が、記録されている事例と違う

構成案は「今回の改修は小規模だから、XDDP のこの成果物作成プロセスをバイパスしよう」
という省略を、PFD の利点として挙げている。

しかし AFFORDD に記録されている適用事例は**省略ではなく代替**である。
トヨタ自動車の事例は、従来の設計書を変更設計書として活用したテーラリングであり、
成果物を作らないのではなく、**既にあるものを充てている。**

XDDP の中核はコーディング留保、つまり3点セットをレビューしてからコードを
変更するという規律である。**成果物の作成をバイパスすれば、この規律が成立しない。**

テーラリングを扱うなら、「省略」ではなく「代替」として、一次資料の事例を出典に書く。

### 5.4 PSP の権利制約が4回連続で抜けている

構成案は「Layer 03 の PFD でチーム全体のフローを定義し、その中の1タスクの中身を
Layer 05 の PSP で実行・計測する」という連携を「美しい階層構造」として提案している。

PSP のスクリプトとフォームは CMU の特別許諾下にあり、派生や改変には SEI の
書面許可が必要である。**「PFD の中で PSP をどう使うか」を書き下ろすことは
翻案にあたりうる。**

| 検証 | 指摘箇所 |
| --- | --- |
| REV-0002 | 第3.2章、決定6 |
| REV-0003 | 第5章 |
| REV-0005 | 第4.3章 |
| **REV-0006** | **本項** |

**4回連続で同じ観点が抜けている。** 登録フォーマットの `rights` を必須にする
決定（REV-0002 決定3）を早く実装しないと、この漏れは続く。

## 6. Front Matter の拡張

記法には、何を記述するかという違いがある。`notation_of` を追加する。

```yaml
kind: notation
notation_of: process        # software | system | requirements | process
```

| 値 | 例 |
| --- | --- |
| `software` | UML |
| `system` | SysML |
| `requirements` | USDM |
| `process` | **PFD** |

これにより、`views/by-kind.md` で記法をまとめたときに、UML と PFD が
同じ「記法」でありながら対象が違うことが一覧で分かる。

PFD の登録例を示す。

```yaml
id: MTH-00NN
name: PFD
name_ja: プロセスフローダイアグラム
layer: 30-team
kind: notation
notation_of: process
axes:
  origin: both
status: referenced-only
applicable_to_solo: true
relates_to:
  - id: MTH-00NN            # XDDP
    relation: contained-by
    note: XDDP の要素として紹介されるが、XDDP 専用ではない
rights:
  holder: 清水吉男 / AFFORDD（派生開発推進協議会）
  terms: 記法は採用してよい。本文の転記と翻案をしない
  verified: 未確認
sources:
  - https://affordd.jp/previous/results.shtml
```

## 7. PFD の説明に出典がない

構成案は「入力成果物 → プロセス（作業）→ 出力成果物をネットワーク状に定義する」と
PFD の動作を説明しているが、出典を示していない。

本リポジトリは「一次資料に当たる」を原則とする。PFD の要素、記法、作図の手順は、
**AFFORDD の概論＆入門ワークショップ資料と、清水吉男『「派生開発」を成功させる
プロセス改善の技術と極意』（技術評論社, 2007）で確認してから書く。**

`rights.verified` を「未確認」のままにしておき、確認した日付を入れるまでは
`status: referenced-only` から動かさない。

## 8. 修正した構成（`30-team/` 部分）

REV-0005 第5章の構成に PFD を加えたものを最終形とする。変更は1行のみである。

```text
├── 30-team/                              # チーム開発プロセス層 (Mid)
│   ├── README.md                         # この階層の定義と境界
│   ├── rup.md                            # 参照のみ。IBM proprietary。レガシー
│   ├── tsp.md                            # 参照のみ。CMU のサービスマーク
│   └── xddp/                             # 3点セットを持つため例外的にディレクトリ
│       ├── README.md                     # 全体像、母体の前提、テーラリングの事例
│       ├── change-request-spec.md        # 変更要求仕様書（USDM 形式）— 3点セット①
│       ├── spec-out-and-tm.md            # スペックアウトと TM — 3点セット②
│       ├── change-design-doc.md          # 変更設計書 — 3点セット③
│       ├── coding-restraint.md           # コーディング留保
│       ├── process-separation.md         # 変更プロセスと機能追加プロセスの分離
│       └── pfd.md                        # 記法。notation_of: process
```

**REV-0005 で既に `pfd.md` を含めていた。** 構成の変更は不要であり、
必要なのは `kind` と `notation_of` の付与と、昇格条件の明文化である。

## 9. 本リポジトリへ反映する決定

| # | 決定 |
| --- | --- |
| 1 | **PFD は `30-team/xddp/pfd.md` に置く。** 独立ディレクトリは作らない |
| 2 | **PFD の `kind` は `notation`。** プロセスとして扱わない |
| 3 | **Front Matter に `notation_of` を追加する。** 値は `software` / `system` / `requirements` / `process` |
| 4 | **昇格条件を定める。** 2件目のプロセス記法が登録された時点で `30-team/process-notations/` を作り移す |
| 5 | **中身が1つのディレクトリを作らない。** 一般規則とする |
| 6 | **`formal-methods/README.md` に、USDM に加えて PFD との違いも書く** |
| 7 | **テーラリングは「代替」として書く。** 一次資料の事例を出典に置く |
| 8 | **PFD の動作の説明は、一次資料を確認してから書く。** それまで `rights.verified: 未確認` |
