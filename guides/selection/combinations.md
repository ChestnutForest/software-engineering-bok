# 組み合わせの制約

## 前提を要するもの

| 手法 | 前提 | 満たさない場合 |
| --- | --- | --- |
| XDDP | 既存の母体 | 新規開発では適用できない |
| TSP | PSP を修めた技術者 | 個人の計測ができないとチームの計画が成り立たない |
| TSP | チーム | 個人プロジェクトでは成立しない |
| DDD | オブジェクト指向 | 構造化手法とは組み合わせにくい |
| SysML | システムズエンジニアリングの文脈 | ソフトウェア単体では過剰 |
| CMMI の評定 | 組織 | 個人プロジェクトでは不可能 |
| ISO 9001 の認証 | 組織 | 同上 |
| SPLE | 組織的な取り組みと将来の派生 | 単発の開発では立ち上げコストに見合わない |

## ほぼ排他のもの

| 軸 | 排他の関係 |
| --- | --- |
| パラダイム | 構造化 ↔ オブジェクト指向 |
| プロセス | RUP ↔ TSP ↔ XDDP ↔ スクラム |
| 再利用戦略 | SPLE ↔ 都度開発 |
| 開発の起点 | 新規 ↔ 派生 |

## 併用できるもの

| 軸 | 例 |
| --- | --- |
| 記法 | UML ＋ Mermaid ＋ USDM。対象が違う |
| 実装プラクティス | TDD ＋ 仕様駆動 ＋ PSP |
| 形式手法 | Alloy で設計を探索し、TLA+ で並行性を確かめる |

## 似ているが別のもの

| 組 | 違い |
| --- | --- |
| SPLE と XDDP | SPLE は**派生が起きる前に**資産を設計する。XDDP は**既にある母体に**変更を加える。時間軸が逆 |
| TDD と仕様駆動開発 | TDD は XP 由来のプラクティス。仕様駆動は AI エージェントへ仕様を渡す進め方。由来も対象も異なる |
| PFD と SPEM | PFD は図法、SPEM はメタモデル。メタレベルが1段違う |
| 構造化分析・設計と JSD | 別系統の手法。JSD を構造化手法の代表例として扱わない |
| SWEBOK と SEBoK | 別分野の知識体系。前者はソフトウェア工学、後者はシステムズエンジニアリング |
